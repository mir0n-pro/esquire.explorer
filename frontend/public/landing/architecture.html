Current Architecture

Two public hosts: esquire.mir0n.pro — administrative GUI (BFF + SPA), opaque session cookie after OIDC code+PKCE login. api.esquire.mir0n.pro — public REST API (gateway direct), Bearer JWT on every request, for service-to-service callers and integrations.

The gateway, the six backend services (bizTree, enyMan, pacMan, keySmith, kcMaster, auKeep), and the BFF — the shape shown above, a program each — run redundant, with optional autoscale, for high availability — spread across separate nodes so losing one keeps the site up. The databases, Keycloak, the message broker, and the Session Store run as a single instance here; each is a third-party platform that brings its own high-availability (clustering / replication), set up by the operator when wanted — outside Esquire's concern.

Esq2025  

The database (Oracle or Postgres); persistent store for all entity data, transactions, permissions, configuration parameters, and the audit log (when triggers are enabled).

Esq2025 audit  

Optional; a separate database (Oracle or Postgres) holding the entity audit log (*_log tables), so audit writes never touch the operational Esq2025.

Messaging Bus  

Three logical channels: the IAM Request-Response Bus carries identity commands from keySmith to kcMaster and acknowledgement replies back; ActiveMQ transport provider; the Entity Broadcast Bus carries entity change events published by enyMan and pacMan to bizTree and other interested consumers; ActiveMQ transport provider; the Audit Broadcast Bus (optional, off by default) carries each committed change event from the entity-updating services (enyMan, pacMan, keySmith) to the audit sink — transport providers: ActiveMQ, Kafka, or Redis.

pacMan — Personal Account Manager

The accounting service; manages account balance operations: deposit, withdrawal, cross-currency transfer; the place where business logic lives; all other services exist to support it.

bizTree    

The entity tree service; maintains an in-memory cache of the business entity tree; serves tree navigation to the frontend; stays current by consuming the broadcast bus. It is a recoverable cache service: a two-buffer anti-entropy design whose background “night-watch” periodically rebuilds a shadow copy from the database, compares the two, and self-heals any drift — so an event missed while the service was down is reconciled automatically, with no restart.

enyMan — Entity Manager

Manages organizations and users; handles create, update, delete, and move operations; publishes entity change events to the entity broadcast bus and also receives from it — a two-way link, so the redundant copies stay coordinated, each aware of the entity changes the other makes.

keySmith

Authentication and access profile service; manages IAS integration and JWT-based authorization; serves access profiles to the frontend; publishes identity change requests to the IAM bus.

kcMaster

Keycloak sync coordinator; the only service that writes to Keycloak directly; consumes identity commands from the IAM bus and executes create / update / delete in the IAM. Also listens on the entity broadcast bus to keep a moved entity's Keycloak path in sync.

auKeep  

Optional; the audit consumer service that drains the Audit Broadcast Bus and writes the *_log tables.

Redis DB

Optional; the alternative non-SQL (document-DB) audit sink — the Redis stream itself holds the audit trail (the stream is the log). Feeding it from the Kafka transport needs one extra component, a Kafka Connect Redis Sink.

gateway  

Spring Cloud Gateway; the API router; routes requests to the appropriate backend service by path and entity kind; validates JWT tokens on every request. Reachable two ways: in-cluster from the BFF on /api/*, and externally at api.esquire.mir0n.pro — the public REST API for non-browser callers (service-to-service integrations, load / smoke harnesses, future mobile or API consumers). External callers carry their own bearer token; no BFF in the loop.

Keycloak

External IAM; issues JWT access tokens; manages user identities, realm configuration, and authentication flows including TOTP; runs as a containerized service.

Esquire Explorer Backend (BFF)

Backend-for-Frontend (Node.js); the administrative GUI entry point at esquire.mir0n.pro. Owns the OIDC code+PKCE flow with Keycloak (/auth/login, /callback, /logout, /me); proxies /api/* to the gateway with bearer injection; caches static entity dictionaries per pod, shared across users; bakes the Angular SPA into its image at build time and serves it on /. The browser never sees the access token — it holds an opaque session cookie. When run redundant, login sessions are kept in the Session Store so any copy can serve any request.

Session Store

Optional; a Redis instance holding the BFF's login sessions, so the redundant BFF copies share them — any copy can serve any request. Only needed when the BFF runs as more than one copy; distinct from the audit-sink Redis.

Esquire Explorer Frontend (SPA)

The user-facing application (Angular); tree-based entity browser and operations UI; consumes the @mir0n-pro/esquire.ui library; communicates only with the BFF via same-origin /auth/* and /api/*, never directly with the gateway or Keycloak. Shipped baked into the BFF image; one deployable.

REST API

Public REST API exposed for gatling-based load / smoke harnesses and other integrations.

Observability Stack

The framework is observable the same way everywhere: metrics, logs, and distributed traces, joined by a single correlation id, so any request's whole story — from the browser, through the service calls, across the message hops — is one search away on one screen. The whole stack can be switched on in any environment, at any moment; whether it is left running is a resource decision, not a capability one. Every piece below is open-source, and any of it can be swapped out — no lock-in, the same rule as the rest of the platform.

Postgres Exporter

Turns the database's own statistics into numbers the metrics store can read.

Prometheus

The metrics store — collects the numbers (rates, timings, counts) from every service and keeps their history.

OpenTelemetry Collector

The traces hub — a separate service that gathers each request's trace from every service, passes it to the trace store, and builds the live map of which service calls which.

Grafana Tempo

The trace store — keeps each request's end-to-end trace, found by the same id as its logs.

Grafana Alloy

The log collector — gathers the log lines from every service and passes them to the log store.

Grafana Loki

The log store — keeps all the logs, searchable, and serves them to the dashboard.

Grafana

The one screen — dashboards for logs, traces, and numbers together; because everything shares one id, a log line, its trace, and its numbers are one click apart.

The compact shape — the same framework in fewer programs

Everything above runs as a program per service. The same code and the same settings also run grouped: mesnie holds enyMan, keySmith and kcMaster, and gateWard holds the gateway together with the tree cache. Eight programs become five — or four in the cloud, where the database writes the audit trail itself and the program that drains it is not needed. Nothing is removed and nothing is rewritten: the same routes, the same messages, the same screens.

Two things move with the grouping, and both are worth knowing. Identity work that travelled the message bus — keySmith asking kcMaster to write to Keycloak — becomes a call inside one program, and a tree read is answered where the request arrives instead of crossing the network a second time. What does not move is pacMan: accounting is a business domain built on the framework, not a part of it, so it stays its own program in every shape — exactly as any domain you build would.

Measured on the cloud deployment, against the same load rig: 27% more work with observability off and 42% more with metrics, logs and traces fully on, 1.5 GiB of memory for the whole application, and 7 pods instead of 13. Every running-stack test suite passes on both shapes, unchanged.

The cost is real and worth saying: services inside one program restart together, scale together, and a crash takes all of them down at once. That is the trade a small installation makes to stop paying for a large one, and it is a deployment choice, reversible at any time.
