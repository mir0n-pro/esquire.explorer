vs Competition

The comparison below is not a promise about where Esquire is headed — it is a mature framework measured as it stands: a complete, working system from database to browser, highly available, fully observable, open at every vendor layer, and running live in production.

It is also written to be checked. Where a comparable project does something better, this page says so, and the claims below are drawn from those projects' own documentation.

The property worth comparing on

Scoping by hierarchy is not rare. Read enough systems that organize people and resources in a tree and most of them limit access by that tree in some form. So "tree-shaped authorization" on its own compares nothing. The difference worth putting side by side is narrower and checkable: can the scope be forgotten?

In many designs it can. The scope is applied per query — a filter fragment added to the statement, a checker called before the work, a session wrapper opened around the call. Each of those works, and each depends on the developer remembering it every single time. A query missing the filter looks exactly like a correct query: nothing in code review, in the build, or in static analysis marks it as unscoped. Enforcement stops being structural one reasonable exception at a time, usually under feature pressure rather than carelessness.

Esquire resolves visibility in the data path, from the caller's position in the tree. There is no per-query filter to write, so there is none to omit and none to review. That is the honest form of the comparison — not we scope by hierarchy and they do not, but here the scope cannot be left out — and it is a property a reader can check by opening the code rather than taking this page's word for it.

Domain-model-driven frameworks — the closest comparison

Apache Causeway (formerly Apache Isis) is the closest project to Esquire's shape. It runs on Spring Boot and generates its UI directly from the domain model, as a webapp, REST or GraphQL, integrating Spring Security and Keycloak. The difference is where the UI definition comes from: Causeway derives it from the domain classes as written, Esquire from runtime server configuration — so in Esquire a field layout change reaches the browser without a redeployment. Causeway does not filter data rows; its permissions grant or veto access to namespaces, types and members, which governs what appears in the UI rather than which rows come back.

Jmix, successor to CUBA Platform, is the closest commercial-grade one — Spring Boot, Apache 2.0, built for large data models and complex internal UIs. It has genuine row-level security and entity-attribute permissions, and so does Esquire. The distinction is hierarchy. In Jmix every constraint is authored per entity class by the developer, as a JPQL clause against the session user's attributes, and its documentation states that there is no native support for a user seeing their own subtree: explicit constraints must be written for each level, with no automatic cascade.

That is the whole argument, and it is worth stating plainly: these are frameworks you build a permission model on; Esquire is one where the hierarchy already is the permission model. Esquire additionally ships the operational floor — high availability, correlated metrics, logs and traces, async messaging — assembled and running rather than left as work.

Authorization engines

OpenFGA, SpiceDB, Ory Keto and Permify model relationships with far more rigour than Esquire does; SpiceDB is the most faithful implementation of Google's Zanzibar paper and runs at very large scale. Alongside them sit policy-as-code engines (OPA, Cerbos, AWS Cedar) and embedded libraries (Oso, Casbin).

Esquire's permission model is less academically rigorous than ReBAC. What it is instead is integrated — part of the entity model and the UI, shipped with the framework rather than operated as a separate service. The common hard case is the same for all of them: point checks are the easy half, and filtering a list to a subtree on every screen is where these systems are actually tested.

Identity and access management

Apache Syncope is Spring-based, multi-database and audit-aware, and solves identity provisioning very well. Its hierarchy exists to support provisioning and reconciliation of users and groups across external systems; Esquire solves the layer above it. Note that Syncope's realms do scope administrative authority hierarchically, which is closer to positional authorization than a simple comparison suggests.

Frontegg is purpose-built for B2B SaaS multi-tenancy and its permission model is strong. It models organizations and users; Esquire's tree continues below the user boundary into arbitrary business entities.

Microservice generators

JHipster generates a scaffold — the starting point for a backoffice rather than a backoffice. After generation the hierarchical entity tree, the positional permission model, the server-driven UI and the async messaging topology are still to be built. A generator that shipped an opinionated permission model would be a worse generator; Esquire starts where JHipster leaves off.

Low-code admin panel tools

Retool, Forest, AdminJS and react-admin generate a working UI quickly, with fields defined in frontend code, so a schema change is a deployment. Esquire is slower to get started with than Retool, and Retool covers a breadth of integrations Esquire does not attempt. The distinction is the destination rather than the speed: a panel over an existing schema is the right tool for an internal data browser and the wrong starting point for a back office whose permission model is a tree. (react-admin is a framework rather than a low-code tool — you write React with it — and is maintained by Marmelab.)
